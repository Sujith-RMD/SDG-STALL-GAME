## Non-obvious things worth remembering
- **The repo has no SQL layer.** The live leaderboard is a Redis sorted set
  (`lb:all`, `lb:day:<YYYYMMDD>`), read by `api/leaderboard.js`. The SQL script is
  standalone; the live trim is `POST /api/admin/trim-leaderboard`.
- **Bug caught by the self-test, not by reading:** if you snapshot the doomed rows
  into a `lb_drop` table, the delete must be `WHERE EXISTS (... IN lb_drop)`, not
  `NOT EXISTS`. `NOT EXISTS` inverts it — keeps the droppers, deletes the keepers.
  The post-trim row-count assertion is what surfaced it.
- **Portable assertion trick** for MySQL 8 / SQLite, which have no anonymous
  ASSERT/RAISE block: insert a 0 into a temp table declared
  `CHECK (ok = 1)`. The resulting CHECK violation aborts the statement. Pair it
  with a `SELECT` of the offending numbers immediately above, since the error
  message itself is generic.
- **Tie handling:** always tiebreak the `ORDER BY` (`score DESC, created_at ASC,
  id ASC`). Without it the surviving row at the 3rd-place boundary is arbitrary
  and can differ between runs.
- **`NOT IN` trap:** never rewrite the keep-filter as `WHERE id NOT IN (SELECT id
  FROM lb_keep)`. A NULL in the subquery makes it match nothing and the delete
  silently removes zero rows. `NOT EXISTS` has no such failure mode.

### 🔴 Redis rank direction — got this wrong twice, do not repeat
Redis sorted-set ranks **ascend by score**, so rank `0` is the **LOWEST** entry.
- To keep the highest 3: `ZREMRANGEBYRANK lb:all 0 -4`  ✅
- `ZREMRANGEBYRANK lb:all 3 -1` keeps the three **LOWEST** scores ❌

Redis has no "keep the top N" command. That is why the route computes the cutoff
score and uses `ZREMRANGEBYSCORE key -inf (cutoff` plus a `ZREM` of the boundary
losers. Both `sql/trim-leaderboard.sql` and the README carry a warning about this.

### Why Lua, and not WATCH/MULTI/EXEC
The trim is read-decide-write. Upstash's REST API is **stateless**, and `WATCH` is
*connection*-scoped, so `WATCH`/`MULTI`/`EXEC` cannot give a read-then-decide
guarantee here. A server-side Lua script is the only atomic primitive available.

### Other findings
- **`EVAL` KEYS/ARGV:** the `score:detail:` prefix is an ARGV, not a KEY (it is a
  prefix, not a key). Getting this wrong silently shifts every argument.
- **No Lua in this environment** (no redis-server, no lua, no docker; WSL exists
  but unused). The fake's `EVAL` delegates to `trimScriptModel`, a JS model of the
  script. Compensated by: a handler-side independent read-back that refuses to
  report success on a mismatch, a fault-injection test for that guard, and a
  structural test asserting the Lua still performs each safety step. **The Lua has
  never been executed against a real Redis.**
- **Side effect to remember:** `GET /api/leaderboard` reports `aggregates.players`
  as `ZCARD lb:all`, so trimming `lb:all` lowers that figure. `stats:*` is
  deliberately not rewritten; the drift is surfaced in the response `warnings`.

### Conventions for admin routes in this project
fail-closed on a missing/weak secret (unlike the rate limiter, which fails open) ·
timing-safe compare · limiter runs *before* the auth check to throttle guessing ·
dry-run by default, an explicit `"confirm": true` required to mutate · reject
unknown body fields so a typo like `dryrun` cannot silently apply · error bodies
must stay generic (a project test greps them for `upstash|redis|token|bearer`).
